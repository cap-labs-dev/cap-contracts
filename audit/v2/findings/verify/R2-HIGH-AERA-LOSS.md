# R2-HIGH-AERA-LOSS — verification of N2 [HIGH] "Aera reserve loss is never recognised"

## Verdict: CONFIRMED

## Why (one paragraph, the decisive reason)
The finding survives every attack. Production wiring gives KEEPER an uncapped `invest` (`Registry.sol:344-348`) and `Stablecoin` keeps no record of what it sent (`invest`/`recall` are pure pass-throughs, `Stablecoin.sol:103-118`); `totalAssets = totalSupply - badDebt` and `unlockedSupply` are computed from supply, never from the reserve, so any shortfall on the Aera leg is invisible to every pricing surface. The "third-party trust" defence does not hold: the defect is not that Aera can lose, it is that Cap has no way to *book* a loss it already knows about — `recognizeBadDebt` is MARKET-only and does `creditBackedSupply -= amount` (underflows with no credit, corrupts utilization with credit), `coverBadDebt` reverts `NoBadDebt` while `badDebt == 0`, and the only role-reachable combination that raises `badDebt` without net-touching credit (`fundCreditBacked(L)` then `recognizeBadDebt(L)`, both MARKET) also raises `totalSupply` by `L`, so `totalAssets` and total payable stay overstated by exactly `L` (my test proves it). Because the protocol already has a socialisation mechanism for the credit leg (squared haircut) and deliberately chose to expose the reserve to an external venue, the missing accounting path is a protocol-owned defect, not an excluded external dependency; the loss is unbounded (no cap on `invest`), needs no attacker, and lands 100 % on the last `L` of unlocked redemptions (verified: earlier redeemers exit at par, the final holder is left with `L` cUSD and `maxRedeem` still advertising it). High is the honest severity.

## What I tried (numbered; include commands run and real output snippets)
1. **Reachability under production wiring.** `contracts/cap/Registry.sol:344-348` wires `invest`/`recall` to `CapRoles.KEEPER`; `ConfigureAccessControl.sol:20` grants KEEPER to `users.keeper`. `recognizeBadDebt`/`fundCreditBacked` are MARKET-only (`Registry.sol:336-342`). No governance misconfiguration needed; `invest` has no bound relative to `unlockedSupply` or the queue. `reserveVault` defaults to `address(0)` (`script/config/WalletUsersConfig.sol:21`) which makes `invest` revert safely — so the bug is only live once RESERVE_VAULT is set, which is the intended deployment.
2. **Ran the workstream PoC.** `FOUNDRY_TEST=audit/v2/tests/scratch/N2 forge test --match-path 'audit/v2/tests/scratch/N2/N2.t.sol' --match-test test_N2b -vv` → `[PASS] test_N2b_aeraLossLandsOnLastRedeemer`, `[PASS] test_N2b_noRecognitionPath`. Read line by line: no pranks of roles the test deployer doesn't legitimately hold (KEEPER/MARKET are the deployer in this harness, matching who holds them in prod), `LossyAeraVault.lose` burns to `0xdead` — a faithful stand-in for a strategy drawdown or fee claim. The PoC demonstrates real loss (Bob holds 100 cUSD, `balanceOf(sc) == 0`, `totalAssets()` still 100), not merely a state the author dislikes. No one-line PoC change makes it pass without a fix.
3. **Angle (c) — searched for any existing recognition path.** Wrote `audit/v2/tests/scratch/verify/R2-HIGH-AERA-LOSS/Verify.t.sol::test_verify_fundCreditBackedThenRecognize_doesNotRepairBacking`: after a 100 loss on a 1000 reserve (real 900), MARKET does `fundCreditBacked(100)` + `recognizeBadDebt(100)`. Result: `creditBackedSupply == 0`, `badDebt == 100`, but `totalAssets() == 1000`, `previewRedeem(totalSupply) == 1000`, `unlockedSupply() == 1000` — shortfall vs. real reserve is still exactly `L`. `coverBadDebt` is irrelevant: it requires `badDebt > 0` and burns the caller's cUSD (treasury would need to hold `L` cUSD, and even then it only works after `badDebt` is raised, which nothing can do). Confirmed `recognizeBadDebt` does `creditBackedSupply -= _amount` (`Stablecoin.sol:150`) — underflow with zero credit, silent utilization corruption otherwise. The only remaining "path" is a UUPS upgrade, i.e. the fix itself.
   Command: `FOUNDRY_TEST=audit/v2/tests/scratch/verify/R2-HIGH-AERA-LOSS forge test --match-path 'audit/v2/tests/scratch/verify/R2-HIGH-AERA-LOSS/*' --match-contract VerifyAeraLoss -vv` → `Suite result: ok. 11 passed; 0 failed` (9 inherited N2 tests + 2 verify tests).
4. **Angle (d) — loss distribution.** `test_verify_lossIsConcentratedNotProRata`: three depositors 400/400/200, `invest(1000)`, 10 % loss, `recall(900)`. Alice and Bob redeem at par (each ends with 1000 underlying); Carol: `maxRedeem == 200`, `redeem(200)` reverts, `redeem(100)` ok, left holding 100 cUSD with zero backing. Distribution is strictly last-out-loses-all, not pro rata — the opposite of what the credit-leg haircut in `_convertToAssets` is designed to do.
5. **Angle (b) — is the uncapped `invest` the real defect?** No: a cap only bounds `L`; `maxRedeem = min(curve, liquid)` only turns the last redeemer's revert into an honest zero. Neither moves the share price or `badDebt`, so the loss is still concentrated on whoever is last, and a rational run (exit at par before liquid hits 0) is still incentivised. The two findings are independent; the Medium is a liveness/view bug, this High is a solvency-accounting bug.
6. **Angle (a) — design intent / third-party trust.** No NatSpec, README or docs claim the reserve leg is loss-free (`grep -rn -i "aera|reserve vault" README.md docs` → nothing; `IStablecoin.invest` NatSpec is one line: "Send underlying reserve to the reserve vault"). Aera V3 `SingleDepositorVault` is a guardian-executed, hooks-constrained strategy vault whose operations can lose value in normal operation; the Aera source is not vendored in `lib/` so the fee mechanics could not be confirmed locally. Regardless, a loss on a venue the protocol *chose* to hold its redemption reserve in is a balance-sheet event the protocol must be able to represent; Immunefi's third-party exclusion covers losses *caused* by a trusted dependency's malfunction, not the absence of an accounting path for an ordinary drawdown. The contract's own design (squared haircut, `_onWithdraw` retirement) shows the intended semantics are pro-rata socialisation — the reserve leg simply lacks the entry point.
7. **Existing mitigations.** None found: no `invested` tracker, no JIT recall in `_transferOut`, no reserve valuation read, no pause on `invest`. `_authorizeUpgrade` (ADMIN) is the only lever.

## Corrections to the finding text (bullet list, or "none")
- "If the deployed Aera vault is a V3 `FeeVault` derivative its fee claim alone guarantees a monotone leak" — should stay flagged as unverified; the Aera source is not in the repo and the team must confirm fee configuration of the actual vault before this is cited as a certainty.
- Add to the "no path" list the MARKET-only `fundCreditBacked(L)` + `recognizeBadDebt(L)` combination: it is the one sequence that raises `badDebt` without net-changing `creditBackedSupply`, and it still leaves `totalAssets`/`unlockedSupply` overstated by exactly `L` (it only dilutes holders through the pot). Closes the last obvious "but governance could…" objection.
- Minor: "Bob keeps 100 cUSD backed by nothing while `totalAssets()` still reports 100" is accurate; note additionally that `maxRedeem(bob)` reports 100 too, so the last holder cannot even detect the loss from the 4626 surface.

## Residual doubt (what would settle it if still uncertain)
Only the likelihood leg: if the deployed Aera vault is configured with zero fees and a hooks whitelist restricted to principal-protected operations (e.g. only stablecoin lending with instant withdrawal), the realistic loss frequency drops and a reviewer could argue Medium. Settling it requires the actual `reserveVault` address, its fee recipient/fee-rate config and its guardian hooks whitelist. Even in that best case the accounting gap remains a latent unbounded-loss path with no representation, which is why I keep High rather than demote.
