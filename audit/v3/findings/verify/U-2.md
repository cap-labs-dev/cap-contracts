# U-2 verification — after a bare upgrade `authority()==0`, so `_authorizeUpgrade`/`setAuthority`/every `restricted` call reverts for everyone

**Verdict:** CONFIRMED-AT-LOWER-SEVERITY (High) — as the irreversibility clause of U-1, not a separate Critical.

## What I checked

**(a) OZ 5.7.0 semantics for `authority()==address(0)`.** `AuthorityUtils.canCallWithDelay` (`node_modules/@openzeppelin/contracts/access/manager/AuthorityUtils.sol`, "last updated v5.3.0") zeroes scratch `0x00..0x40`, then `staticcall(gas, authority, …, 0x00, 0x40)`; if the call *succeeds* it reads `immediate := mload(0)`, `delay := mload(0x20)`. A staticcall to `address(0)` (or any codeless account) **succeeds with empty returndata** — it is not a precompile and does not revert — so the pre-zeroed words are read back: `(immediate=false, delay=0)`. `AccessManagedUpgradeable._checkCanCall` then takes the `!immediate && delay==0` branch and reverts `AccessManagedUnauthorized(caller)`. The "could an empty-account call be read as allowed" attack does **not** land: allowed requires a non-zero first return word, which only a contract that answers can produce, and `authority()` is pinned at 0. Verified with a probe that calls the library directly against `address(0)`, an EOA, and (as a sanity check for the mechanism) a contract whose fallback returns `1` — only the last is "allowed" (`test_a_canCallWithDelay_zeroAuthorityIsUnauthorizedNotAllowed`). `setAuthority` requires `_msgSender()==authority()==address(0)`, which no transaction can satisfy. `UUPSUpgradeable.upgradeToAndCall` has no admin path; `_authorizeUpgrade` is `restricted` on both contracts (`Stablecoin.sol:333`, `Wrapper.sol:102`). No other writer of the AccessManaged namespace exists in HEAD. Confirmed.

**(b) Any calldata / any rescue implementation after the bare upgrade.** Matrix in `test_b_nothingRescuesAfterBareUpgrade`: `setAuthority` from the deployer, a holder and the v1 AccessControl → `AccessManagedUnauthorized(sender)`; `upgradeToAndCall({HEAD, Migrator} × {"", initialize(...), migrateStablecoin(...)})` → `AccessManagedUnauthorized(this)` (the gate fires before the delegatecall, so the calldata is irrelevant); plain `initialize` → `InvalidInitialization()`; `mintCreditBacked/burnCreditBacked/invest/recall/setReserveVault/recognizeBadDebtInReserve` → `AccessManagedUnauthorized`; stcUSD second upgrade and `setAuthority` → same. Permanent after the bare upgrade: confirmed.

**(b) Is "permanent" overstated?** Yes, in the sense the brief asks about: before the bare upgrade the v1 gate (`checkAccess(bytes4(0))` on `0x7731…`) authorises an upgrade to *any* implementation, so an intermediate implementation that writes `openzeppelin.storage.AccessManaged` (and the U-1 slots) followed by HEAD gives a working, upgradeable proxy with HEAD unchanged (`test_b_orderMatters_v1GateMustStillBeLiveWhenMigratorLands`, and the full recovery in U-1's `test_b_twoStepMigrationFullyRecoversBothProxies`). The finding's own "Likelihood" already concedes this (a reinitializer executed non-atomically bricks at tx 1). So the accurate statement is: **a bare upgrade to HEAD is an irreversible brick; a migration step must run while the v1 implementation is still the one authorising upgrades** (either atomically in `upgradeToAndCall` with a reinitializer, or via an intermediate implementation).

**(4) Severity.** U-2 has the same root cause as U-1 (no `__AccessManaged_init` on the live proxies) and the same trigger (a privileged operator sends the bare upgrade). Counted separately it double-books one mistake. Its distinct contribution is the irreversibility, which is what lifts U-1 from "temporary outage" to High. No attacker, no third party, a viable path exists, and a fork rehearsal fails on the first restricted call. High, folded into U-1.

**(5) Existing coverage.** None in `test/` (see U-1).

## Recommendation to the lead

**Merge into U-1 at High.** Keep the mechanism paragraph (staticcall-to-empty-account → unauthorized) as the explanation of *why* the brick is irreversible; it is correct and non-obvious. Drop the secondary recommendation to make `_authorizeUpgrade` "tolerant of the migration window" by reading the v1 `cap.storage.Access` slot from HEAD — it bakes a permanent second authority into a contract that is supposed to have one, and the atomic `reinitializer(2)` inside `upgradeToAndCall` already removes the window. Keep the AccessManager note: in my run the manager's admin could upgrade with no `setTargetFunctionRole` at all (OZ's default role for unconfigured selectors is `ADMIN_ROLE`), so the timelock must hold ADMIN on the new manager before the batch, and that default also means every `restricted` selector on cUSD is admin-callable until roles are configured — worth one line in the release checklist.
