# U-1 verification — live proxies cannot be initialised into HEAD; bare upgrade leaves every HEAD-only slot at zero

**Verdict:** CONFIRMED-AT-LOWER-SEVERITY (High, not Critical) — and merge with U-2 into one finding.

## What I checked (independently of the author's reasoning)

**(c) v1 Initializable is namespaced and sits where HEAD reads it.** v1 worktree (`main @ 695c828`) `yarn.lock` resolves both `@openzeppelin/contracts` and `contracts-upgradeable` to **5.4.0**; `CapToken`/`StakedCap` inherit `Initializable` from OZ 5.x, so `_initialized` lives at `erc7201("openzeppelin.storage.Initializable")` = `0xf0c5…6a00`, the same slot HEAD's `initializer` modifier reads. Read directly from mainnet (`cast storage`, publicnode, block ~25,977,014): both `0xcCcc…cccC` and `0x8888…8888` hold `0x…01` there; linear slot 0 is untouched. `initializer` then evaluates `initialSetup = (1==0 && top) = false`, `construction = (1==1 && code.length==0) = false` → `InvalidInitialization()`. There is no `reinitializer` anywhere in `contracts/` (`grep reinitializer contracts/` is empty). Confirmed.

**(d) No slot overlap between v1 and HEAD.** v1's namespaces are `cap.storage.{Vault,Minter,FractionalReserve,Access,StakedCap,…}`; HEAD's own are `cap.storage.{Stablecoin,PremiumVesting,ERC7540AsyncRedeem,ERC7540Operator,Wrapper}` plus OZ's. The only shared string is `cap.storage.Wrapper`, which v1 uses for an unrelated OFT wrapper contract that never ran on the stcUSD proxy, and HEAD `Wrapper` declares no variables of its own anyway. My test reads 8 slots from every HEAD-only namespace on a freshly-initialised v1 proxy and finds all zero; mainnet `cast storage` agrees for `openzeppelin.storage.AccessManaged` (0 on both), `openzeppelin.storage.ERC4626` (0 on cUSD; `0x12|cUSD` on stcUSD) and `cap.storage.Access` (`0x7731…` on both). So: nothing is corrupted, but nothing HEAD needs is present either — exactly the finding. One re-word: on **stcUSD** the ERC4626 namespace *does* survive (`asset()==cUSD`, decimals 18) because v1 `StakedCap` is OZ `ERC4626Upgradeable`; only `authority` and `optedIn` are missing there. "Every slot … left at zero" is true for cUSD, not for stcUSD.

**(3) Numbers.** Re-derived offline with supply 84,884,291e18, `underlyingDecimals==0`: `totalAssets() = backing·10^0/10^18 = 84,884,291`; `previewDeposit(1e6) = 1e6·10^18/10^0 = 1e24`; `previewMint(1e18) = ceil(1e18·10^0/10^18) = 1`. All match the finding. `requestRedeem` succeeds and moves shares out of the wallet; `claimableRedeemRequest` then reverts (queue math divides through `asset()==0`). Live figures also match: cUSD supply 84,884,291.50, stcUSD supply 74,726,468.68.

**(5) Existing coverage.** `test/` has no fork test and no test that upgrades a proxy carrying pre-existing v1 state; `test/integration/Deployment.t.sol` and the `Stablecoin.t.sol` upgrade tests all start from `initialize` on a fresh proxy. `script/` is dead v1 code with no migration path (`DeployInfra.sol` deploys fresh CREATE3 proxies). Nothing covers this.

## Strongest attack and why it only partly lands

**(b) "No path / permanent" is overstated.** The v1 `_authorizeUpgrade` is `checkAccess(bytes4(0))` on the v1 `AccessControl` (`0x7731…`); it authorises an upgrade to *any* implementation. So the timelock is not forced into a bare upgrade: it can install a one-off intermediate implementation that writes the OZ/HEAD namespaces and then upgrade to the unchanged HEAD through HEAD's own `restricted` gate. I wrote a ~40-line raw-slot `Migrator` (not in HEAD, gated on the v1 access slot) and ran the four-tx sequence v1→Migrator(+migrate)→HEAD on both proxies: `asset()==USDC`, `underlyingDecimals==6`, `authority()==AccessManager`, `stablecoin()==cUSD`, `optedIn(stcUSD)==true`, name/symbol preserved, `instantRedeem(1e18)` pays 1 USDC, `deposit(5e6)` mints 5e18, wrapper deposit/redeem work, `mintCreditBacked` works, and both proxies remain upgradeable by the manager admin and by nobody else (`test_b_twoStepMigrationFullyRecoversBothProxies`). HEAD is therefore *deployable* onto the live proxies today without touching `contracts/` — but only if the operator knows to do it that way. The gap in the deliverable is real: HEAD has no reinitializer, no script, no test, and the natural `upgradeToAndCall(impl, initialize…)` reverts, so the obvious fallback is exactly the bare upgrade that bricks.

**(a)/(b) after a bare upgrade** the escape closes: the Migrator, `initialize`, `setAuthority` and every calldata variant revert (`test_b_migratorCannotBeAppliedAfterBareUpgrade`; full matrix in U-2). So the "permanent" clause is correct *conditional on* the bare upgrade having landed.

**(4) Severity.** Impact if it happens is total and irreversible (redemption-frozen, non-upgradeable token; transfers still work). But the trigger is a privileged operator executing a specific wrong transaction, with no attacker, no third-party actor, and a viable two-step path already available; any fork rehearsal (the author's own `U_LiveUpgrade.t.sol` is one) fails on the very first post-upgrade call. "Likelihood: certain" is therefore certain *for a bare upgrade*, not certain for the release. That is the classic "privileged mis-step causes irreversible loss" shape, which I rate High rather than Critical.
